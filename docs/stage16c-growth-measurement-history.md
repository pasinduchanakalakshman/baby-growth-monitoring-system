# Stage 16C: Growth Measurement Entry + History Foundation

## Measurement Data Flow & API Contract

### Add Measurement API
- **Endpoint**: `POST /api/v1/growth/measurements`
- **Request Fields**:
  - `visit_date` (Required, Date YYYY-MM-DD)
  - `weight_kg` (Required, Float > 0)
  - `length_height_cm` (Optional, Float > 0)
  - `currently_breastfeeding` (Optional, Boolean)
  - `formula_feeding` (Optional, Boolean)
  - `solid_foods_started` (Optional, Boolean)
  - `diarrhea_last_14_days` (Optional, Boolean)
  - `fever_last_14_days` (Optional, Boolean)
  - `cough_last_14_days` (Optional, Boolean)
- **Validation**:
  - Visit date cannot be before baby's date of birth (Status `400`).
  - Duplicate visits for the same date are rejected (Status `400`).
- **Response Fields**: Includes the input fields plus calculated `age_days`, `verified_waz`, `verified_haz`, and ID fields.

### History API
- **Endpoint**: `GET /api/v1/growth/history`
- **Behavior**: Returns a list of stored `GrowthMeasurementResponse` objects, ordered chronologically by `visit_date`.

### Ownership
- Authentication is strictly required. No `child_id` or `user_id` inputs are provided by the client. The backend resolves the authenticated mother's session to retrieve the single associated baby profile and attaches new measurements to it.

## Visit-Based Methodology
- Measurements are explicitly visit-based.
- **No Interpolation Rule**: The application does not fabricate missing visits or estimate missing values (like height) for ML continuity.
- Missing optional data is strictly stored and displayed as `null` (or "Not recorded").
- Scientific calculations like WAZ/HAZ are generated by the backend and merely presented by the frontend.

## Form Validation
- `weight_kg` must be greater than 0.
- `length_height_cm` if provided, must be greater than 0.
- Future visit dates are not allowed.
- Visit dates before the child's Date of Birth are prevented client-side (backed by server-side validation).

## History Behavior & Empty States
- History shows a list/cards of chronological measurements (latest first via client-side reversal of backend's ascending sort if needed, or keeping chronological order for a timeline view).
- If no history exists, an empty state prompts the mother to "Add First Measurement".
- Unrecorded optional fields are explicitly shown as "Not recorded".

## Responsive UX
- **Mobile**: Stacks layout vertically, with full-width cards for history.
- **Tablet/Desktop**: Uses multi-column grids for form sections (Measurement, Feeding, Illness).

## Limitations
- Editing or deleting measurements is not currently supported by the backend, and thus the UI does not expose edit/delete capabilities.
- Advanced forecasting and WHO charts are stubbed out and await Stage 16D implementation.
